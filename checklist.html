AI調達の仕様検討で確認する8項目

調達事例 仕様を検討 評価基準 事例の解説 資料の確認方法

仕様書を書く前に「何を要求するか」だけでなく、「どこまでAIに任せるか」「根拠がない時にどう振る舞わせるか」「どの条件を必須・評価・参加資格に置くか」を切り分けます。

これは法令・政府標準・必須要件の一覧ではありません。2026年10月3日時点で根拠と適用範囲を確認した調査記録と公式一次資料から、実案件で差が出た論点を「確認する問い」に変換したものです。各案件の条件を他自治体へそのまま転用せず、リンク先の調査記録の適用範囲を確認してください。

どこで生成AIに回答・文章を生成させるか

「AIを使う / 使わない」では粗すぎます。生成を許す工程と、人間や固定データに残す工程を分けます。

神戸市税務ボイスボットは音声・文脈理解にAIを使いながら、市民への回答は市提供FAQ由来の回答データに限定し、AIによる回答生成を禁止しています。一方、神戸市の仕様書作成支援AIではLLMが修正案を生成し、利用者が採用・不採用を選択します。埼玉県の県民向けAI相談は生成回答を許しつつ、根拠表示と根拠なし時の回答制御を組み合わせています。

確認すること: 生成を許す対象、最終判断者、固定回答が必要な領域、誤生成時の影響を工程ごとに分けているか。

神戸市税務ボイスボット → 神戸市仕様書作成支援AI → 埼玉県AI相談 → 回答を生成しない条件の調査記録 ↗ 人が修正案を選ぶ条件の調査記録 ↗ 埼玉県公式Q&A ↗

RAGを必須・任意・対象外のどこに置くか

RAGが仕様にないことと、組織としてRAGを使わないことは同じではありません。

おうみ共同調達ではRAGは公募時の必須機能で、参加団体ごとに100GB以上を要求しています。京都市2026汎用生成AI調達ではRAGを当該調達の対象外としていますが、理由は既存サービスでRAGニーズを満たしているためです。

確認すること: RAGの要否、対象データ、容量、権限分離、既存サービスとの役割分担を「今回の調達範囲」として明示できているか。

おうみ共同調達 → 京都市汎用生成AI → おうみのRAG要件の調査記録 ↗ 京都市のRAG対象範囲の調査記録 ↗ おうみ公式仕様書 ↗

回答根拠と「分からない」の扱いをどう定義するか

RAGを入れるだけでは、回答時の根拠提示や根拠不足時の挙動は決まりません。

埼玉県は県民向けチャットボットにも元データや参照ページへのリンク等を提示する想定を明確化し、根拠が見つからない場合は回答が不明であると回答できることを要求しています。焼津市は登録データをできる限り優先する一方、一般知識からの回答を100%排除できない前提を公式Q&Aで受け入れています。

確認すること: 引用・リンクの見せ方、根拠を確認できない場合の応答、一般知識の利用範囲、正答率やテスト方法を別々に定義しているか。

埼玉県AI相談 → 焼津市生成AI → 埼玉県の根拠提示に関する調査記録 ↗ 焼津市の根拠提示に関する調査記録 ↗

Q&A・訂正後の有効要件をどう管理するか

比較対象は最初に公開された仕様書ではなく、後続資料を反映した応募時の条件です。

おうみ共同調達では公式質問回答により、LLM数、Deep Research、テンプレート数、自律的エージェント、認証、ネットワーク条件などが変更されています。元仕様だけを読み続けると、既に緩和・変更された条件を現行要件として扱うことになります。

確認すること: 仕様書・Q&A・訂正を一つの変更履歴として管理し、変更前と変更後を識別できるか。

おうみ共同調達 → 公募中の条件変更に関する調査記録 ↗ 公式質問回答 ↗

必須・加点・参加資格をどう分けるか

同じ条件でも、調達上の役割が違えば意味は大きく変わります。

北海道2026 RAG調達ではISO/IEC 27001は提案の加点ではなく入札参加資格です。越谷市2024では月100万文字以上が必須である一方、「上限なし」は必須ではなく、上限量に応じた評価加点の対象です。

確認すること: その条件が「満たさないと参加できない」「満たさないと仕様不適合」「満たすと評価が上がる」のどれかを明示しているか。

北海道RAGサービス → 越谷市生成AI → 北海道の参加資格に関する調査記録 ↗ 越谷市の最低条件と評価項目の調査記録 ↗

データ取扱いの対象をどこまで具体化するか

「国内」「保存しない」「学習しない」は、対象を省略すると別の条件に読めます。

大府市は市データの国内保存を要求しつつ、生成AI APIの接続先所在地そのものを国内に限定していません。埼玉県の公開Q&Aは、LLMサーバの保存禁止を「推論完了後の永続保存」と解釈し、推論中のコンテキストウィンドウ等での一時保持は対象外としています。

確認すること: 入力・出力・ログ・RAGデータ・一時保持・永続保存・学習利用・API接続先を同じ言葉でまとめず、対象別に条件を書いているか。

大府市生成AI → 埼玉県AI相談 → 大府市の保存先とAPI接続先の調査記録 ↗ 大府市公式Q&A ↗ 埼玉県公式Q&A ↗

選定・契約・稼働を別々に確認できるか

候補者の選定結果だけでは、契約締結や実稼働を確認したことにはなりません。

群馬の共同調達は共通選定後に各契約予定団体へ再見積を行い、団体ごとに個別契約します。おうみ共同調達も参加自治体ごとのサービス利用契約を持ちます。共通選定の状態を案件全体の契約・稼働へ自動的に丸めると、団体ごとの差を失います。

確認すること: 選定、契約締結、契約最終仕様、サービス開始を別の証拠で確認できるか。共同調達なら主体別の状態差があり得るか。

群馬共同調達 → おうみ共同調達 → 共同調達の選定・契約段階に関する調査記録 ↗ 群馬県公式資料 ↗

実証・本格導入・今回の調達範囲を区別できるか

機能が高度でも、案件自体が本格導入フェーズとは限りません。

福島県2026「生成AIサービス導入支援業務」はRAG・ガバナンス・活用促進まで含みますが、公式仕様では実証結果を分析し「次段階の本格導入」に向けた要件・体制・運用ルールを整理する事業です。京都市のRAG対象外も、組織全体の機能不在ではなく今回調達のスコープ境界でした。

確認すること: 今回の調達が実証、限定導入、本格導入、更新のどこに位置し、今回対象外の機能を別基盤で満たしていないか。

福島県2026実証 → 京都市汎用生成AI → 福島県の実証段階に関する調査記録 ↗ 福島県公式仕様書 ↗

チェックリストの使い方

既存自治体の文言をコピーする前に、自組織で決める条件と、その条件が適用される範囲を明確にします。

1. 未決事項を出す

8つの問いに対して「決定済み / 要協議 / 今回対象外」を置き、対象外には理由と別の受け皿を残します。

2. 実案件を比較する

リンク先の案件詳細で、仕様、質問回答・訂正後の要件、評価基準、根拠資料との対応を確認します。

3. 文言ではなく役割を移す

他自治体の条件をそのまま転記せず、なぜその条件を必須・加点・対象外に置いたかを自組織の前提に合わせて決めます。

法令、国のガイドライン、組織内の情報セキュリティ規程、個人情報・機密情報の取扱い等はこのチェックリストだけで代替できません。

案件データベースで比較する → 5つの設計論点を読む → 調査記録（GitHub）を見る ↗

これは仕様を検討するための問いです。事例の適用範囲は、リンク先の調査記録と公式資料で確認してください。
