# AI調達仕様検討の回答ベンチマーク V1 — 方法論

## 目的と検証範囲

通常のWeb検索だけとRepository-firstで、同じ実務上の問いへの回答品質、根拠、調査負担、完了時間を比較する。勝敗の方向は固定しない。本成果は設計・Gold作成までであり、どちらのRunnerも実行していない。

既存26案件からの目的抽出による20問である。全国の自治体調達や質問頻度を代表する無作為標本ではない。自然な実務者の問いを設計者が構成したもので、実務者から収集した実際の問い合わせではない。測るのはこの問題集合と実行環境での回答支援効果であり、自治体の調達品質やベンダーの優劣ではない。

基準Repository: `Josh-Temple/public-sector-ai-procurement-japan`

Repository-firstの知識を固定するcommit: `35d66cf710215f251da9809034249de868f6d24e`。

Goldの原典確認日: 2026-10-01。日本の会計年度は4月始まり。質問で特定された過去公募・公開仕様の条件を答える。現在の稼働や最新製品仕様を求める試験ではない。

## 問題選定

回答を試す前に構成・重みを固定した。単純検索4問を含み、20問すべて10点で等重み。最大の案件でも4問への登場に抑える。主カテゴリは重複なしで集計し、複数の論点を含む問もある。カテゴリ別の成績も必ず併記する。

| 主カテゴリ | 問題 | 数 |
|---|---|---:|
| A 単純事実 | 001–004 | 4 |
| B 必須・任意・加点／条件 | 005, 018 | 2 |
| C 質疑による変更 | 007–009 | 3 |
| D scope・condition | 010–013 | 4 |
| E 調達・利用段階 | 014–015 | 2 |
| F 証拠境界 | 016–017 | 2 |
| G 業務特化AI | 019 | 1 |
| H 案件比較 | 006, 020 | 2 |

001–004は、単一の公式ページ・PDFで核心が分かる対照問題。単純事実でも想定数と実績、選定と契約、上限と契約額を混ぜないことを求める。

`evals/REQUIREMENT_REASONING_V1.md` の24問は削除・上書きしていない。候補として使い、既知の失敗だけを全問にすることを避けた。Goldの `candidate_origin` に変換元を記録した。EVAL-001/002、004/023、013/015はそれぞれ実務文脈に合わせ統合。内部schema分類を問うEVAL-007は採用しない。案件IDを知らないと解けない問いも採用しない。細かい実装論点を繰り返す大府のチャンク代替問題等は枠数・重複を考慮し不採用。

京都市RAG比較と鹿児島県利用規模の候補は、登録原典URLの今回のHTTP 404により採用せず、本文を直接検証できる既存案件に置き換えた。これは品質を保証するための原典確認基準であり、Web-only/Repository-firstの成績を見ての選別ではない。ただし再取得できる資料への偏りは残る。除外URLは既存Source registryの `SRC-kyoto-2026-general-genai-spec` と requirementsの鹿児島県source URL。元データの過去検証を今回fresh確認済みに書き換えてはいない。

自治体名・案件名・年度は「解くべき対象の識別」であって検索経路のヒントではない。これらを取り除くと問題が不成立になる。Publicには資料名・URL・ページ・質問番号・変更後数値・schema名・採点軸・理由説明を追加していない。設問そのものが求める比較軸は両条件に同じように提示する。

## Goldの検証と限界

各問の原典本文を公式URLから再取得し、仕様、必要な質疑、実施要領・選定結果の関係を確認した。PDFはファイル内の1始まりのページ番号と節・質問番号を固定。表の列対応はローカル抽出を併用し、神戸の回答生成条件と北海道の容量条件はページ画像でも確認した。文書に「案」とある場合は公募段階の案として扱う。URL到達のみをGold検証の代用にしていない。

GoldにSource ID・URL・位置、現在のstructured row、Claimの状態、role別review、case-level reconstructability、stage projectionを記録する。行がないことや `not_assessed` は不存在としない。個別要件が追えることと契約最終状態が追えることも分ける。原典・構造化データの関係を確認した設計者による再検証であり、別の独立Judgeによる二重検証は未実施。実行前にJudgeだけの別セッションでGoldを確認することを推奨する。

今回、過去に `source_unavailable` だった大府・焼津・北九州のExcel、神戸FAQ、北海道ZIPはHTTP 200で取得できた。取得成功は全セル・全条件の検証を意味しない。既存データの取得状態をこのPRで一括変更しない。Goldはこの差を明記し、Runnerが原典を取得して正しく更新して回答した場合は同じ採点を認める。016の未取得Excelを必須の不足理由にしない。公開Q&Aの限界は別に残る。018は再取得した北海道ZIP内の業務処理要領を本文確認して作成した。

017の「見つからない」は公式案件ページのリンク一覧・募集要領・公募仕様案・公開Q&A等の確認範囲に限る。全Webで契約後文書が存在しないことをGoldとしない。Runnerが別の公式最終仕様を発見した場合はURL・版・適用段階をJudgeが確認し、Goldと矛盾するという理由だけで減点しない。更新の問題だった場合は両条件の当該問を保留し、同じ版で再採点・必要なら再実行する。

原典のファイルhashは保存するが原典全ファイルのdurable snapshotは保存していない。URLから同じバイトを取得できる保証はない。hash一致は同一性の確認であり正しさの証明ではない。将来原典が消えた場合は、原典を読めるものとして比較し続けず、変更・取得不能を記録して両条件を同じ基準で扱う。

## 実行前に固定する条件

実行管理者が、回答を見る前に次をrun manifestへ記録する。

- benchmark version、Public SHA-256、Gold SHA-256（Judge側のみ）、上記のRepository ref。
- run ID、実行日、条件、完全なmodel ID・reasoning設定、ツール版、検索エンジン、PDF/HTML/ZIP/Excelの取得手段、ネットワーク・context上限。
- Memoryと過去会話を使わない独立した新規セッション。設計者セッションをRunnerへ流用しない。
- 全問の順序、反復番号、タイムアウト設定、時計の計測手段。
- 原典が両条件で取得可能かの環境確認。片方にだけZIP取得手段を与えない。

最低実施は条件ごとに20問の独立した1バッチ（40回答）で、結果は記述的な1回観測。一般的な性能向上とは断定しない。再現性の確認には同じmodel設定で3反復以上を推奨するが、実施数は結果を見る前に固定する。

1バッチ内の文書再利用は許容する。これは実務の複数質問をまとめて調べる効果を含む試験である。各バッチでは同じ順序を両条件に使用し、反復間では記録済みseedで無作為に並べ替える。並べ替えは昇順IDリストへPython標準ライブラリの `random.Random(seed).shuffle` を適用する。初回の既定seedは20261001で、順序は020, 006, 007, 005, 018, 009, 001, 019, 014, 004, 003, 010, 002, 016, 015, 013, 017, 012, 011, 008。単純対照を先に並べたID順で本番を走らせない。条件の実行順も反復ごとに交互にする。別条件の回答・ログをもう片方へ見せない。問題単位の独立セッションに変更する場合は別の実験として報告し、バッチ結果と混ぜない。

1問の調査・回答は実測できる場合12分を上限にする（追加質問のための一時停止を含めず、ツール待ちを含む）。時間計測がない場合は上限遵守を確認不能と記録する。タイムアウト時はその時点の回答を固定し、未回答の要素は0点。失敗問を黙って除外しない。監督可能な時計がない場合の時間比較は行わず、品質・確認できた操作数だけ比較する。

## 条件別の許可範囲

両条件とも、質問本文と同じ実務文脈を渡し、公式資料に裏付けられた短い回答と根拠を要求する。Goldの採点項目・カテゴリ・難易度は渡さない。原典へのアクセス、一般検索、PDF/ZIP/Excel読み取り能力を同じにする。

### Web-only

`BENCHMARK_V1_WEB_ONLY_RUNNER_PROMPT.md` の本文だけを渡す。通常のWeb検索から開始する。Repository、GitHub、過去チャット、Memory、このプロジェクトの索引・構造化データ・分析を参照しない。検索スニペットにプロジェクトのGold・問題別解答が現れた場合も利用せず漏洩として報告する。公式資料以外のページは探索補助にできるが、それ自体をGoldの代用にしない。

### Repository-first

Public本文と次の実行指示だけを新規セッションへ渡す。Gold・QA・Source receipts・本方法論の問題選定節を渡さない。

> 対象Repositoryのcommit `35d66cf710215f251da9809034249de868f6d24e` を固定して利用してください。INDEXとAGENTSから必要なdata、sources、claims、researchへ進み、根拠の適用範囲・確認状態・鮮度を確認してください。evalsディレクトリ全体、PR・Issue・後続commit・ベンチマーク設計資料を閲覧しないでください。既存知識を優先して再利用し、過去公募の安定した事実に毎回Web検索を強制する必要はありません。not_assessed、source_unavailable、not_public、conflicting_sourcesを無視して確定しないでください。必要な範囲は公式原典で再確認し、取得できなければ確認限界を回答に残してください。Repository記載と一次資料が食い違う場合は一次資料を優先し差を記録してください。既存知識にない値を推測しないでください。全問について短い実質的回答、確認した根拠、資料・検索・時刻の観測ログを返してください。別条件の回答や過去の会話・Memoryは使わないでください。

固定commitに本Goldは含まれない。既存claims等に質問に関連する知識があることは測定したい介入であり、漏洩とはしない。一方、回帰evalの想定回答を読むことは直接の試験問題再利用になるため両条件で禁止する。

## Contamination対策

本repoはpublicであり、Goldを保存・mergeする以上、機密化・アクセス不能は保証できない。「Judge-only」は実験上の閲覧権限であり公開URLの技術的なアクセス制御ではない。この限界を隠さない。

管理者は次を実行する。

1. Web-onlyにはプロンプト本文だけをコピーし、repo/PRリンクや前の会話を渡さない。
2. 検索時にはGitHubとそのraw/CDN、当該projectの転載を除外する。可能なら検索結果・閲覧を公式ドメイン中心に技術的に制限する。除外条件は全Web-only反復で同一に記録する。
3. Repository-firstは固定commitのcheckoutを使い、evalsを参照対象から外す。GoldのあるmainやGitHub全文検索へ移動しない。
4. 誤閲覧・答えを含むスニペットの混入は即記録する。読み取った後に「使わない」と宣言してそのまま比較しない。漏洩したバッチは比較から隔離し、新規セッションでバッチを再実行する。元の結果も隠さず残す。
5. フィルタできず露出を監査できない実行は「露出を制御できない探索試行」と表示し、厳密な独立比較としない。

モデルの訓練時の既知情報まで除去することはできない。同じmodel・独立セッションを使い、観測できる閲覧と過去文脈の漏洩を管理する。

## 採点（全問10点、合計200点）

JudgeはRunnerの条件名・model名を伏せた回答を、Goldと公式原典に照らして採点する。ログの条件判定や効率集計は採点を固定した後に行う。出典の形式から条件を推測できる可能性は残るため、完全な盲検とは主張しない。

| 軸 | 点 | 判定 |
|---|---:|---|
| factual correctness | 4 | 各問F1/F2各2点。完全2、核心は正しいが一部欠落1、誤り・欠落0 |
| scope / condition | 2 | 各問の2項目各1点。範囲・条件が回答に保持されている |
| evidence quality | 2 | F1/F2各1点。引用した公式一次資料が当該事実を支持し、PDFページ・節・質問番号等で追える |
| uncertainty / boundary | 1 | 各問で定めた境界を守る。明記が必要な016/017では単なる無断定では足りない |
| no prohibited inference | 1 | 禁止推論を断定しない |

全く回答を試みていない空欄・欠落問は0点。部分回答・理由を伴う棄権は各軸で採点する。質問で明示した案件・年度をそのまま受けていることが分かれば、短い回答で同じ案件名や年を復唱する必要はない。条件が答えの本質である場合は明記を必要とする。

内部IDの使用、Goldと同じ表現、GoldのURLとの完全一致を要求しない。公式の別資料も同じ根拠品質として認める。事実引用に結び付かないURL羅列は証拠点を与えない。Repository-firstも、既存行から一次資料とlocatorの対応を再利用できるなら毎問原典を再openする必要はない。その場合は「原典fresh確認」ではなく「保存済み根拠を再利用」と記録する。

答えの分からない問に境界を示して棄権しても、既知の数値等の事実点は自動で与えない。誠実な未確認は誤った断定と区別して集計する。誤った結論に矛盾する正しい文を後付けしても完全点にしない。

独立したJudge確認を推奨。初回Judgeと再確認者に不一致があれば、根拠・採点理由を残し裁定する。Goldの更新が必要なら変更理由を公開し、両条件へ同じ変更を適用する。差が小さい場合に特定問だけ重みを変えない。

## 観測ログと指標

操作イベントは `event_id, run_id, benchmark_id, timestamp, event_type, query_or_url, document_id, result_status, reused_from_event_id, observed_by` を記録する。条件名は採点用回答から除き別manifestに保持する。時刻はISO 8601で、実際に観測したものだけ。失敗も含む。機械ログがある場合は優先し、自己申告のみならその制約を明記する。

| 指標 | 定義 |
|---|---|
| total score | 全20問の5軸合計、0–200。問題別・カテゴリ別の点数も示す |
| factual error count | 原典と矛盾する独立した断定の数。単なる未回答は別のmissing factとして数える |
| unsupported assertion count | 資料から支持されない独立した断定の数。推測の数値・期間・仕様・実績等。真偽未判定でも支持がなければ該当 |
| scope-loss count | 対象・単位・条件・段階を失った断定の数。Goldの必要条件の欠落はomissionとして別のreason codeを付ける |
| amendment-miss count | 当該問の公式後続解釈・変更を落とし、旧状態を回答した独立要件数。単にQ&Aを引用しないだけなら該当しない |
| evidence-boundary error count | 未確認をなしとする、公募を契約最終とする、非公開を変更なしとする等の独立した断定数 |
| primary-source citation rate | GoldのF1/F2計40採点単位のうち、回答内の公式引用が支持する単位数 / 40。文書が同じでも単位で数える。回答した単位だけを分母にした補助値も併記（回答単位0なら補助値はnull） |
| source documents opened | バッチ内で本文を実際に取得・開いたユニーク公式文書数。HTML/PDF/Excel/ZIP内文書は文書単位。ZIP容器自体は別のcontainer取得として記録し本文文書へ二重算入しない |
| web searches | 実行した検索query数。複数queryを含む1ツール呼出は複数検索。失敗queryも数える。find/click/openとRepository内rgはWeb検索に数えない |
| answer completion time | 各問の問題作業開始から回答確定までの実測壁時計秒。検索・ツール待ち・回答生成を含む。バッチ全体の実測秒も記録 |

source documents openedにはGold設計時の閲覧を算入しない。Repositoryファイルのopen数・内検索数・初回checkout/setup秒は別途記録して、Repository側のコストを隠さない。初回取得に含まれる全ファイルを「読んだ」としない。Runnerが実際に本文を参照したファイルを数える。初回setup込み総時間とsetup後時間を両方報告する。セッション内で公式文書を再利用した場合は、ユニーク数を増やさず再利用イベントを記録する。

問題別のdocument countは当該問で参照した文書（既取得の再利用を含む）と新規open文書を分ける。バッチ合計はユニーク文書のunionで求め、問題別countを足さない。Repository文書・Web公式文書を別列にし、さらに両者合計の取得イベント数も示す。検索結果snippetだけは文書openではない。

同じ断定がfactual・scope・boundaryの複数errorに該当してよい。ただし同一断定の言い換え・繰り返しは一つの `assertion_id` とし、各カテゴリ内で重複しない。カテゴリの件数を足して独立エラー総数と称さない。採点軸は独立評価するため同じ誤りが複数軸に影響し得るが、追加の恣意的な罰点は付けない。

ログがない操作数・時間は `null` / `not_measured`。0としない。modelの「考えた秒数」表示・推定読書時間を実測の代用にしない。ネットワーク障害や検索索引の変化はそのまま記録し、両条件に影響する環境変更は再実行又は明示した感度分析で扱う。

## 分析計画

主指標は200点中のtotal scoreの条件差（Repository-first − Web-only）。補助として5種類の誤り、40単位の一次引用率、資料open・検索回数、実測時間を示す。単純検索4問と残る16問、全カテゴリを別集計する。品質を時間に混ぜた独自総合指標は作らない。

1反復では問題別差・全体差のみ記述し、統計的有意・普遍的効果を主張しない。反復した場合も同案件・同資料の質問間には依存があることを記載する。中央値・範囲を反復単位で示し、必要なら案件の依存を考慮した分析を別途行う。20問を独立な全国サンプルとみなした検定は行わない。

双方が正解なら効率の差、Repository-firstが棄権したなら既存知識の不足・再確認の失敗、Web-onlyが良ければ索引・データの鮮度や誘導の問題として解釈する。効率比較はタイムアウト率と品質差を併記し、速い未回答を改善と扱わない。Gold作成・コーパス構築・維持コストは今回の回答時短に含まれず、総投資価値はこの試験だけで決められない。

## 完了判定

構造QAと内容QAが通り、全問の一次資料本文確認・全項目のGold・Public分離・同一rubric・汚染対策・観測定義があることを設計完成とする。独立実行結果もRepositoryの優位性も本PRでは報告しない。独立Gold再レビューと環境・汚染管理は後続実行の準備条件として残る。
